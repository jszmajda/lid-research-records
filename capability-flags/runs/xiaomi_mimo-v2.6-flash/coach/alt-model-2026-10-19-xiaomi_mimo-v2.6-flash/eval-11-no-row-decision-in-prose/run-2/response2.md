**F1 — High. The job queue holds accepted jobs only in process memory, so a restart silently breaks the HLD's first tenet.** `docs/intent/job-queue/job-queue-design.md` (Architecture, line 14) states that the queue lives "entirely in process memory" and that "jobs that were accepted but not yet dispatched before a restart are gone, and members resubmit them" — and the same doc's Context (line 10) says the mini-PC "takes unattended OS updates and the occasional power blip," so restarts aren't a hypothetical edge case, they're a described operating condition. Under *tenet cascade* (design nodes should lean the way the HLD's tenets and goals say to lean, with exceptions recorded), this mechanism runs directly against tenet 1 — "A submitted job is a promise: members should be able to upload and walk away" — and against the goal "evening upload, overnight print, morning pickup — with no member present." The two docs never use the same words, which is exactly how this drift hides: a member who uploads at 9 pm, loses the job to a 2 am update reboot, and finds an empty printer at breakfast has been failed by the design in a way no spec currently names or tests. If it sits unflagged, every future session that touches durability will re-derive this tension from scratch, and the project's central promise stays formally stated but operationally false. You have three remedies, and the choice is yours: **change the design** (persist accepted jobs — e.g., in the SQLite file the registry already uses — so a restart rebuilds the queue alongside the printer state), **record the exception** (a Decisions row stating that accepted-but-undispatched jobs are dropped on restart, naming tenet 1 as the tenet traded against and why — cheap hardware and small-surface goals are the honest rationale), or **revise the tenet** (soften "a promise" to match at-most-once delivery). Recording the exception is the lowest-cost option and, note, it also closes F2 below; you may still prefer a different remedy for the tenet itself.

**F2 — High. The durability choice itself is under-captured: it survives only as Architecture prose, with no Decisions row.** Under *decision capture* (*docs carry current intent* — a live decision deserves a full row a cold reader can act on), the test is forward from the landed state: a cold reader of `job-queue-design.md` holding its Decisions table and the HLD above it would absolutely question "jobs are gone on restart" — the printer-registry LLD just chose a single SQLite file precisely because it "fits the mini-PC" (`printer-registry-design.md` line 25), which makes "why doesn't the queue also persist?" the obvious next question, and the table gives them nowhere to find the answer. They can see *that* members resubmit, but not what was given up (durability, the promise tenet) or what cost was accepted (member re-uploads after every blip), because the reasoning lives only in a paragraph that reads as description rather than as a weighed choice. Left as is, every future session that considers touching startup, persistence, or the registry store will re-open the question — and may "helpfully" half-fix it by persisting files but not queue order, producing a coherence mess no one chose. The smallest capture that settles it is **a fuller Decisions row** in `job-queue-design.md`'s table along the lines of: *Queue durability → In-memory only, rebuilt by polling printers → Persisted queue rejected: adds write path and recovery logic to a service sized for a modest mini-PC; accepted cost: accepted jobs are lost on restart and members resubmit — this trades tenet 1 ("a submitted job is a promise") for the small-surface goal, deliberately.* Since the registry's SQLite choice is a sibling decision the reader will line this up against, a decision doc documenting the full options space (memory vs. SQLite vs. file log) is an option if you want it on record — but a table row is the right-sized capture here; a decision doc isn't required. If you take the F1 route of changing the design instead, the row changes to record *that* choice (persist via the shared SQLite file, say) and both findings close together.
