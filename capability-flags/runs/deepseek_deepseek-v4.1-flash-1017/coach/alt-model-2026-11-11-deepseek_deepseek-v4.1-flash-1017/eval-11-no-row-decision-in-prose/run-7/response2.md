**F2 — High. Accepted jobs live only in process memory, which collides with the HLD's promise tenet.**

The queue design says plainly that jobs are "held entirely in process memory," and that after a restart "jobs that were accepted but not yet dispatched before a restart are gone, and members resubmit them" (`docs/intent/job-queue/job-queue-design.md:14`). Its own Context names the conditions under which that happens — the mini-PC "takes unattended OS updates and the occasional power blip" (`:10`) — so this isn't a rare corner; it's a described operating condition. The HLD tenet it runs into is "A submitted job is a promise: members should be able to upload and walk away" (`docs/high-level-design.md:20`), and the LLD's "members resubmit them" is the exact behavior the tenet says members shouldn't have to do. Two details sharpen it: uploaded G-code already survives on disk by content hash, so the expensive part is durable while the cheap part — the queue entry — is not; and the EARS layer never states the loss at all. `QUEUE-004` only says the system rebuilds farm state by polling printers on startup, so an implementation that silently dropped or persisted accepted jobs would satisfy every spec equally. That's the *LLD sufficiency* gap riding along with the tenet conflict.

Under *tenet cascade* — the design should lean the way the HLD's tenets point unless an exception is recorded — the cost of leaving this is that the first power blip turns the system's headline promise into a support conversation, and the next agent reading either the LLD or the specs has no way to tell whether the loss is deliberate. Under *decision capture* (decisions that stay live once landed are recorded with what was given up), the missing Decisions row is the other half: the design has chosen job loss and documented the mitigation ("resubmission is cheap") only as body prose, not as a decision. If you leave the behavior as-is, that mitigation is the accepted cost worth naming in the row.

You have three remedies, and they're genuinely different bets rather than a ranked list — pick the one that matches what you intend:

- **Change the design to persist accepted jobs.** The registry already uses a single SQLite file (`printer-registry-design.md:14`), so a durable queue table or append-only file fits the same modest-hardware constraint the "service stays small" tenet names — this doesn't obviously trade against that tenet. It does mean `QUEUE-004` grows a clause: on startup, restore accepted-but-undispatched jobs as well as polling printers. This is the option that makes the tenet true rather than qualified.
- **Record the exception.** Add a Decisions row to `job-queue-design.md` choosing in-memory queue over persistence, naming the rejected alternative (durable queue entries) and the accepted cost (jobs accepted before a restart are lost; members resubmit; cheap because G-code is content-hashed on disk), and naming the tenet traded against. Per the follow-up guidance, recording the exception also closes the *decision capture* half of this finding. You'd also want a spec stating restart behavior, since right now the arrow is silent on it — otherwise the exception lives in prose the code may never honor. No decision doc is warranted here; this is a row-sized decision.
- **Revise the tenet.** If best-effort acceptance really is the intent, narrow the HLD tenet to match — something like "a dispatched job is a promise" or "accepted jobs are best-effort across restarts" — and let the queue design's current behavior stand. This is an HLD-level change, so it cascades to both leaves' reading of their own guarantees.

If you go with the design change, that's a code-behavior change to the job-queue leaf, so walk it through `/linked-intent-dev` starting from the LLD rather than editing specs ad hoc — the cascade there is job-queue design → `QUEUE-004` (and likely a new restart spec). If you go with the exception row, it's a direct edit to `job-queue-design.md`; no `/update-lid` needed since the configuration itself is sound.
