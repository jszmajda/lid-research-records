**The in-memory queue vs. the "job is a promise" tenet (F3).** In `docs/intent/job-queue/job-queue-design.md:14`, the queue is "held entirely in process memory," and on restart "jobs that were accepted but not yet dispatched before a restart are gone, and members resubmit them." The HLD's first tenet (`docs/high-level-design.md:20`) says "A submitted job is a promise: members should be able to upload and walk away," and the first goal says the member should never need to be present. Under *tenet cascade* — design nodes should lean the way the HLD's tenets and goals say to lean — the two never use the same words, but the condition that matters is described right there in the design: the mini-PC "takes unattended OS updates and the occasional power blip." A reboot at 2 a.m. silently discards every accepted overnight job, which is precisely the failure the promise tenet exists to prevent, and the member has no way to know until morning. This is worth fixing before tests and code exist, because the current design bakes the loss into the architecture. The remedy here is genuinely yours to choose — the skill offers three without picking one: change the design (persist accepted-job records; you already run SQLite for the registry, so a small queue table would be cheap on the mini-PC), record the exception (a Decisions & Alternatives row naming the tenet traded against and why the risk is accepted — for example, "power blips are rare and resubmission is tolerable"), or revise the tenet so it no longer promises durability. If you pick "record the exception," that row also closes the decision-capture gap on the same choice; if you pick "change the design," the choice stays live and deserves a fuller row anyway, since a cold reader would otherwise still ask why the queue was in memory. Whichever you pick, the actual restart behavior should get an EARS spec — right now `QUEUE-004` covers rebuilding farm state from printers but never states that undispatched jobs are lost, so the arrow currently documents the recovery half of the behavior and leaves the loss half implicit.

**Two related findings that ride on the same choice (F8, F7).** The job-identifier decision (`job-queue-design.md:32`) says base32 slugs "recycle after 90 days," but the queue is in memory, so a cold reader can't reconstruct what tracks the slug space across a restart — `docs carry current intent, written to be read cold` means the page itself should settle that, not a past conversation. If you persist the queue, persist the slug ledger with it; if you keep jobs in memory, say where the 90-day clock lives. Separately, `HLD is architecture and rationale` — the HLD carries *why* architecture-level choices were made — and this is exactly the kind of choice the HLD should reflect: it is project-global (it trades against a project tenet) yet appears only in leaf prose, with no Success Metrics or Key Design Decisions section at the root. A line in the HLD recording "queue durability is deliberately sacrificed for smallness" (or the decision to persist) would keep the root honest instead of leaving the leaf to carry an architecture-level trade alone.
