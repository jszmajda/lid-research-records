**F1 — High. The queue's in-memory design works against the HLD's own promise under a condition the LLD itself describes.** `job-queue-design.md:14` holds the queue "entirely in process memory," and rebuilds only the *running* picture on startup by polling printers: "jobs that were accepted but not yet dispatched before a restart are gone, and members resubmit them." Four lines earlier, the same Context says the mini-PC "takes unattended OS updates and the occasional power blip." So the condition is not hypothetical — it's documented as routine. Put that beside the HLD's tenet "a submitted job is a promise: members should be able to upload and walk away" and the goal "evening upload, overnight print, morning pickup — with no member present," and the overnight window is exactly when accepted-but-undispatched jobs sit longest and when nobody is there to notice they vanished. A member uploads at 21:00, three jobs deep in the PLA queue; an unattended update restarts the service at 02:00; at 08:00 they collect nothing and learn they needed to be present after all. This is *tenet cascade* — leaf mechanisms should lean the way the HLD's tenets and goals say to lean, or record the exception naming what was traded. The reason this one matters more than a typical durability gap is that the tenet is the project's whole value proposition over the chat-channel-and-USB-stick status quo; a future session reading `job-queue-design.md` cold sees resubmission described as normal operation and will build more behavior on that assumption — retry UX, notification copy, staff tooling — each of which gets more expensive to unwind. Worth noting that nothing forces the choice: `printer-registry-design.md:14` already persists to a SQLite file on the same box, so durable storage is present in the system and the queue opts out of it. Three remedies are open and the pick is yours: change the design (persist accepted jobs, most cheaply into the SQLite file the registry already owns, or a sibling one); record the exception as a Decisions & Alternatives row in `job-queue-design.md` naming the tenet traded against and why volatility is acceptable; or revise the tenet in `docs/high-level-design.md` so it promises something the design actually delivers (e.g. a promise that holds once dispatched). If you take the design route, the new behavior wants EARS coverage too — a spec for surviving restart would sit naturally beside `QUEUE-004`, which currently specifies only the farm-state rebuild.

**F2 — High. The volatility choice has no Decisions row, so a cold reader can't see what it bought.** `job-queue-design.md` carries a Decisions & Alternatives table with three rows — scheduling order, job identifiers, upload size limit — and each does the hard part well: it names the rejected alternative and the accepted cost ("shortest-job-first rejected: members game it by splitting prints; accepted cost: one long job can hold a class for hours"). The in-memory decision, which is the most consequential of the four, isn't in the table at all; it lives as a prose sentence in Architecture. Under *docs carry current intent, written to be read cold* — rationale and considered alternatives that a fresh author would write from current intent belong on the page — the test for a row is forward from the landed design: would a cold reader still question this choice or be tempted to reverse it? Here they clearly would, and the neighbouring SQLite file makes the reversal look free, which is exactly the situation a row exists to head off. Without it, the next session either re-derives the reasoning from scratch or "fixes" the volatility without knowing what was protected — simplicity on modest hardware, presumably, but the doc doesn't say, so nobody downstream can weigh it. The remedy is small: a fourth row in the existing table, in the same voice as the other three — decision, chosen, and a rationale that names what persistence would have cost and what the accepted loss is. That's the right size of capture here; this doesn't need a decision doc, which is reserved for choices where researched options were weighed against criteria at a resolution a future reader could re-run. And note the overlap with F1: if you take the "record the exception" remedy there, the row you write satisfies both findings at once — a single row naming the tenet traded against and the cost accepted closes this one too. The other two F1 remedies don't; if you change the design, the row still wants writing for whatever the new choice gives up, and if you revise the tenet, the row records why the queue stays volatile.

**F11 — Low, but it belongs to this thread.** The HLD's three tenets are an unordered list, and two of them pull in opposite directions on precisely this question: "a submitted job is a promise" argues for persistence, "the mini-PC is modest hardware; the service stays small" argues against it. *Tenets capture forward-looking preference* — a tenet is a one-line tie-breaker for decisions no spec covers — and an unordered list of tenets that can conflict doesn't break the tie; it hands the next session the same open question F1 is about, which is how the conflict got resolved silently in the first place. Ordering them in `docs/high-level-design.md` so the promise outranks smallness (or doesn't) pre-decides this class of question for every future session, not just the queue-durability one.
