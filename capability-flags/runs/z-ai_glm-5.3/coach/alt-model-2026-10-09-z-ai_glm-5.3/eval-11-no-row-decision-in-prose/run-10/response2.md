**F1 — High. The queue keeps accepted jobs only in process memory, which quietly defeats the project's own promise tenet.** `docs/intent/job-queue/job-queue-design.md:14` states the queue is "held entirely in process memory" and that jobs "accepted but not yet dispatched before a restart are gone, and members resubmit them" — while the same file's Context (line 10) says the mini-PC "takes unattended OS updates and the occasional power blip," and the HLD's first tenet (`docs/high-level-design.md:20`) says "a submitted job is a promise: members should be able to upload and walk away," with the flagship goal being evening upload → overnight print → morning pickup, no member present. Put those together: the failure condition the docs themselves describe (a blip or overnight update) lands exactly in the window where jobs sit accepted-but-undispatched, and the walked-away member has no signal to resubmit — QUEUE-004 only recovers *running* jobs by polling printers, so the queued tail is silently lost. Under *tenets capture forward-looking preference* — tenets exist so mechanisms lean the way the user chose — this mechanism leans against tenet 1; and under decision capture within *docs carry current intent*, the choice is invisible *as a choice*: it sits in Architecture prose as settled fact, with no Decisions row (the registry got a store row — "Single SQLite file" at `printer-registry-design.md:26` — the queue never did), so a future session inherits it as intended and never re-weighs it against the tenet it costs. That's the compounding risk: the drift looks like design, not drift.

The real tension here is tenet 1 ("the job is a promise") against tenet 3 ("the service stays small") — persistence is the classic small-cost-for-durability trade. The remedy is your call, and there are three honest options:

- **Change the design.** Persist accepted jobs — an append-only journal, or a table in the SQLite file the registry already opens (tenet 3's cost stays low, since SQLite is already on the box). On startup, restore the pending queue alongside QUEUE-004's running-job poll. This would cascade: a new spec (something like "When the service starts, the system SHALL restore accepted-but-undispatched jobs from the persistent store"), its test written first, and a Decisions row for the store choice.
- **Record the exception.** Add one row to job-queue's Decisions table naming the trade explicitly: *in-memory queue chosen; accepted cost — a restart loses queued jobs, traded against the "job is a promise" tenet, because [your why]*. This also closes the decision-capture half of F1 — one row is the smallest capture that settles it; a decision doc would be overkill for this.
- **Revise the tenet.** If losing queued jobs on a blip is genuinely acceptable — members are physically in the space most days, resubmission is cheap — then the tenet is over-promising and should say what's true (e.g., "a *dispatched* job is a promise"), with the goal text adjusted to match.

Which of these is right depends on how often blips actually happen and how mad a member gets finding an empty queue in the morning — that's a judgment about your makerspace, not about the docs.
