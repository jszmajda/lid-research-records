**F1 — High. The queue's restart behavior defeats the HLD's core tenet under conditions the docs themselves treat as routine.** `job-queue-design.md:14` holds accepted jobs "entirely in process memory" and states "jobs that were accepted but not yet dispatched before a restart are gone, and members resubmit them." The LLD's own Context (`job-queue-design.md:10`) says the mini-PC "takes unattended OS updates and the occasional power blip" — so restarts are a described operating condition, not an edge case. Set that against the HLD's first tenet (`high-level-design.md:20`), "A submitted job is a promise: members should be able to upload and walk away," and the first goal (line 26): evening upload, overnight print, morning pickup, with no member present. A member who uploads at 9pm and loses power at 11pm arrives to no part *and no job* — and the LLD's own mitigation, "members resubmit them," requires the member to notice the loss, which presences them exactly when the goal disclaims presence. This is the *tenets capture forward-looking preference* / tenet-cascade pattern — the design should lean the way the HLD says to lean — and it flags because no Decisions row records the exception naming the tenet traded against. The cost of leaving it unresolved: the first implementation session encodes the loss as intended behavior, and every later session inherits a queue that quietly breaks its own promise. One honest complication to weigh: the in-memory choice plausibly leans on tenet 3, "the service stays small" — that tension sits inside the HLD between tenet 1 and tenet 3. Worth noting, though, that the registry already persists to a SQLite file on the same disk (`printer-registry-design.md:14`), so "stays small" doesn't obviously force the loss.

The most questionable choice in the design tree is the only major one with no Decisions & Alternatives row.** The Decisions table (`job-queue-design.md:29-32`) records scheduling order, slug format, and the upload cap — each with a rejected alternative and an accepted cost — but the in-memory queue appears only as architecture fact in prose (line 14). Under *decision capture* (from *docs carry current intent* — a choice a cold reader would still question needs its reasoning on the page), this row fails the sweep: a cold reader holding the doc tree would question this choice first, because the asymmetry is conspicuous — the registry survives restarts in SQLite while the member-facing promise doesn't. Why it matters: this is exactly the decision a future session re-derives on its own — a crash-recovery feature, a "where did my job go?" bug report — and an unrecorded choice gets contradicted or silently re-made differently each time it comes up.
