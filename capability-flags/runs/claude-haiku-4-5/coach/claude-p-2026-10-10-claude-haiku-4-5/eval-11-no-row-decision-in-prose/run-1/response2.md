**F2 — Medium. The job queue's in-memory storage creates a failure mode that is mentioned in the design but not formalized as a spec.**

The job-queue-design document says: "jobs that were accepted but not yet dispatched before a restart are gone, and members resubmit them." This is a real behavioral constraint with testing implications — if you write a test that submits a job, then crashes the service, you need to know whether the job will still be there. Currently, QUEUE-004 ("When the service starts, the system SHALL rebuild farm state") describes startup recovery for running jobs (the registry polls printers), but there's no spec that explicitly states the guarantee (or lack thereof) for queued jobs: **"When the service restarts, jobs accepted but not yet dispatched are lost; members must resubmit."** This belongs in the QUEUE spec file because it's a behavioral edge case that tests and code need to implement against. Under *LLDs close enough of the solution space* — specs bridge the gap between design intent and implementation — a vague mention in prose leaves the agent guessing whether "lost on restart" is a promise, a known risk, or an oversight. The cost of not formalizing it is that whoever writes the test suite may not cover this case, and the code may accidentally try to persist the queue (wasting effort) or, worse, silently lose data in production without the team realizing it. **Recommended action:** Add a new spec to job-queue-specs.md: `QUEUE-006: When the service restarts, jobs that were accepted but not yet dispatched are lost. Members must resubmit.` (Consider whether this deserves a more specific ID structure — e.g., `QUEUE-RESTART-001` — if restart behavior grows into its own subsystem later.)

**F3 — Medium. The choice to use in-memory storage is an architectural decision that should live in the HLD, not buried in an LLD.**

The HLD jumps from "Approach" directly to "Architecture: Two design nodes" without explaining *why* the queue is in-memory or *why* heartbeat-based discovery is the right lever. These choices flow from the tenet "The mini-PC is modest hardware; the service stays small," but that connection is left implicit. A future reader — or the team a year from now when the service grows — should be able to find the reasoning at the HLD level. Right now, the decision lives only in job-queue-design.md §2 ("entirely in process memory"), which means every agent who wants to understand the architecture has to read both the HLD and both LLDs to reassemble the reasoning. Under *HLD is architecture and rationale* — the HLD carries why the system is shaped the way it is — the missing piece is a brief "Key Design Decisions" section or an expanded "Architecture" section that names the two core choices (in-memory queue for simplicity, heartbeat-driven discovery for responsiveness on modest hardware) and ties them to the tenets. This is not a gap in the current implementation (the design is sound), but it becomes one if the project evolves: if someone later argues "we should use a database to survive crashes," the HLD is the right place to replay why in-memory was chosen, and that conversation is harder without it being there. **Recommended action:** In CLAUDE.md's HLD, add a "Key Design Decisions" section (or expand "Architecture") to name the two architectural choices — in-memory queue and heartbeat-driven discovery — with a one-sentence rationale tying each to the tenets. No need to duplicate the detail from the LLDs; just make the reasoning transparent at the architecture level. This is a light edit to the HLD; no command needed.

Together, F2 and F3 point at the same underlying pattern: the decision to accept a crash-loss risk is real and deliberate, but it's not explicit enough for the arrow to walk it forward cleanly.
