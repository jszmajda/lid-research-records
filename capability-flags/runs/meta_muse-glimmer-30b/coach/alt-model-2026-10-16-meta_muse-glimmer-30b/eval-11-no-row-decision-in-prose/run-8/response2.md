The in-memory queue is the most visible tension in the job-queue segment right now.

**Observation.** `docs/intent/job-queue/job-queue-design.md:14-15` states the queue is *“held entirely in process memory”* and *“jobs that were accepted but not yet dispatched before a restart are gone, and members resubmit them.”* The restart behaviour is only partially spec’d: `docs/intent/job-queue/job-queue-specs.md` QUEUE-004 says *When the service starts, the system SHALL rebuild farm state by polling each registered printer for its current job*, but there is no spec for what happens to accepted-but-undispatched jobs on restart. The choice is not in the Decisions & Alternatives table — the table covers scheduling order, job identifiers, and upload size limit, but not durability.

**Principle.** *Tenets capture forward-looking preference* — a tenet is a one-line tie-breaker for decisions no spec covers — and *docs carry current intent, written to be read cold* — with the keep-side that a decision lives at the lowest node that dominates it and a decision doc/row records the choice a cold reader would still question. The current design text records the outcome without naming it as a deliberate choice.

**Why this matters for printfarm.** The HLD tenet *“A submitted job is a promise: members should be able to upload and walk away.”* `docs/high-level-design.md:20` is directly undercut by a restart that silently drops queued work. That is a tenet / goal conflict, dimension 19: under an operating condition the docs describe — a mini-PC that *“takes unattended OS updates and the occasional power blip”* `docs/intent/job-queue/job-queue-design.md:10` — the mechanism defeats the promise it is supposed to keep. Because the loss is described as architecture fact rather than a recorded decision, a cold reader cannot tell whether the loss is intentional, acceptable, or an oversight. If it stays implicit, future sessions will assume the promise holds and design around it, compounding the drift.

**Recommended action.** Treat this as both a decision-capture and a tenet-conflict finding. The smallest useful capture is a fuller Decisions & Alternatives row in `docs/intent/job-queue/job-queue-design.md` naming the rejected alternative — e.g., persisting the queue to disk — and the accepted cost — e.g., members must resubmit after a restart. With that row in place, pick one of the three tenet-conflict remedies:
* change the design to persist accepted jobs so the promise holds,
* keep the in-memory design and record the exception explicitly, naming the tenet *“members should be able to upload and walk away”* that is traded against and why, or
* revise the tenet to reflect the actual service contract.

If you keep the current behaviour, add an EARS spec for restart loss so the arrow is explicit: e.g., *When the service restarts, the system SHALL discard accepted-but-undispatched jobs and require member resubmission.* That makes the intent walkable and testable, and it closes the gap between the LLD description and the spec layer.
