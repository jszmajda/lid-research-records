Honest answer: I don't think it earns one, and the length of the debate is exactly the wrong reason to write it.

The decision-doc guidance has a hard carve-out: **don't write one for a choice that affects only its own node, however long the debate ran.** This choice lives entirely inside the previews worker — the HLD tenet says so explicitly, the review API sees none of it, no other component is sized around it. A cold reader of the LLD will find three named options with clear tradeoffs; the Decisions & Alternatives row gives them everything they need to reconstruct the judgment.

The thirty-meeting, 180-message effort reflects how much the *process* cost, not how live the *choice* will stay for a future reader. A decision doc memorializes something a cold reader would re-litigate; a well-filled table row is sufficient when the choice is bounded to one node.

My recommendation: a full Decisions & Alternatives row in the previews LLD, with all three options named and the screening-scan protection rationale written out. That's genuinely useful to a future maintainer. A standalone doc would be overhead that doesn't add coverage.
