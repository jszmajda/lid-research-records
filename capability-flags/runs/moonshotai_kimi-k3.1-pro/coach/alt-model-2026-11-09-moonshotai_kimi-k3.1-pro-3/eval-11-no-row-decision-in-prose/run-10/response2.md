**F2 — High. The queue’s restart behavior conflicts with the submitted-job promise.** The HLD says, “A submitted job is a promise: members should be able to upload and walk away” (`docs/high-level-design.md:20`), but the queue holds accepted jobs entirely in process memory and explicitly loses undispatched jobs on restart, requiring members to resubmit them (`job-queue-design.md:14`). Under *tenet cascade* — component mechanisms should uphold the HLD’s preferences or explicitly record an exception — the documented power blips and unattended OS updates make this a realistic contradiction rather than a theoretical edge case. Members can walk away only while the service remains running, and future implementers receive conflicting guidance about whether accepted-job durability matters. Choose one of three remedies: **change the design** so accepted jobs survive restarts; **record an exception** in the job-queue Decisions table naming the tenet and explaining why resubmission is acceptable; or **revise the tenet** so it accurately describes the weaker promise. If you change the design, run `/linked-intent-dev` with that durability change so the HLD, LLD, specs, tests, and eventual implementation stay coherent.

**F3 — High. The reasoning behind accepting that data loss is missing.** The architecture states the in-memory design and its consequences, but the Decisions & Alternatives table records only scheduling, identifiers, and upload size (`job-queue-design.md:27-33`). Under *decision capture* — a choice that cold readers would question should preserve what was rejected and what cost was accepted — durability is precisely such a choice: the document acknowledges occasional power loss but does not explain why losing accepted work is preferable to durable storage, especially when the registry already uses SQLite. Without that record, a future session cannot tell whether resubmission is deliberate intent or an early implementation shortcut frozen into the design. Add a queue-storage decision row identifying the alternatives considered, the rationale, and the accepted restart cost. If you choose to record a tenet exception for F2, that same row can close both findings; it should explicitly name the submitted-job tenet being traded against.

My recommended next step is therefore to **settle the accepted-job durability contract before writing implementation code**. If the promise remains as written, specify restoration of accepted and in-flight jobs, idempotent redispatch behavior, and retention semantics through `/linked-intent-dev`. If resubmission remains the intended experience, tighten the HLD/LLD language and capture the exception in one decision row so members and future maintainers get the same contract.
