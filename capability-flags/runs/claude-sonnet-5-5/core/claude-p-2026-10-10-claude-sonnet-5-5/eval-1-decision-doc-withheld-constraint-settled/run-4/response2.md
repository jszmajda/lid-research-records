Overkill, I'd say. The Decisions row in the registry LLD is enough.

The skill's test is whether a cold reader of the finished design would find the choice non-obvious, not how hard it was to decide. Here:

- **An inherited constraint settles it.** The HLD tenets forbid runtime network access, which rules out the HTTPS directory and the managed search service. A reader who sees SQLite next to that tenet won't be tempted to reverse it.
- **It stays inside one node.** The index is private to the registry, and the certificate interface is unchanged. No sibling node is being sized around the result.
- **One line carries the rationale.** The row names the rejected options, says why, and notes the cost: each kiosk rebuilds its own index at import.

Your back-and-forth was real, but it doesn't change the answer. The skill says not to offer a doc for a choice an inherited constraint settles, "however long the debate ran."

A decision doc would earn its place only if the choice were still live. That could happen if the no-network tenet were ever relaxed, for example by a lab network route. At that point the options would trade against each other on cost, maintenance, and richer search, and a doc could carry that. The row's rationale already points at the tenet as the reason, so a future reader would know what to revisit.
