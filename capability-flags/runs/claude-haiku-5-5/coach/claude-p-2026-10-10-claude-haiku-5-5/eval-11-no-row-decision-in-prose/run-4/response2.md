**F1: Accepted jobs vanish on restart, which works against the promise tenet.** The HLD's first tenet says "A submitted job is a promise: members should be able to upload and walk away." The job-queue LLD keeps the queue "entirely in process memory," and says that after a restart, "jobs that were accepted but not yet dispatched … are gone, and members resubmit them." The same LLD says the mini-PC "takes unattended OS updates and the occasional power blip," so a restart is a routine event. A member who uploads in the evening and walks away can lose the job overnight with nobody present, which is the HLD goal "with no member present." This is *tenet cascade*: a mechanism working against a tenet or goal, where the two share no wording. The docs describe the condition but never record the trade. Why it matters: a future agent reads the tenet and the LLD and can't tell which one wins. Consider picking one of three remedies:
- **Change the design:** persist accepted jobs and their order, so a restart recovers the queue. QUEUE-004 would still rebuild printer state by polling.
- **Record the exception:** keep the in-memory queue and add a Decisions row that names the promise tenet as the one traded away, and why. This also closes F2.
- **Revise the tenet:** narrow "promise" so it covers only what the service can guarantee, for example jobs accepted while the service is up.

**F2: The in-memory queue is a live decision with no row.** The choice appears only in the Architecture paragraph. The Decisions & Alternatives table has rows for scheduling order, job IDs, and upload size, but not for queue storage. *Decision capture* asks whether a cold reader, holding the landed design, would still question the choice. Here they would, because the restart loss sits in the same doc. The row would also need the rejected alternative and the cost accepted. If you keep the design, the smallest capture that settles it is a row like this:

> | Queue storage | In-memory; printer state rebuilt by polling on start | Persistence not chosen. Accepted cost: jobs accepted but not yet dispatched are lost on restart and members resubmit. Conflicts with the promise tenet; see HLD. |

If you change the design, F2 becomes the row for the new choice, with the same structure.

**F3: A design concern, separate from F2: persistence may be cheap here.** The registry already keeps its state in a single SQLite file on this same mini-PC, and its Decisions row says nothing else needs concurrent writers. A jobs table would reuse a store that's already running, at the cost of one write per accept, reorder, and dispatch. That cost sits against the "service stays small" tenet, and the docs don't show whether the team weighed it. The question that decides this: was the in-memory queue a considered trade-off, or a default nobody revisited? If it was a default, the first remedy in F1 is probably a small change, and F2 goes away with it.
