These two findings cover the same choice, so I'll walk through them together.

**F2 (high). A restart can silently drop jobs members were promised.** The job queue keeps accepted jobs only in process memory (`job-queue-design.md:14`). On restart, anything accepted but not yet dispatched is gone, and members have to resubmit it. The LLD's own context says the mini-PC takes unattended OS updates and the occasional power blip (`:10`), so restarts are expected, not rare. Under *tenets shape the design*, the first tenet says "a submitted job is a promise: members should be able to upload and walk away" (HLD:20). The goal "Evening upload, overnight print, morning pickup, with no member present" (HLD:26) depends on the same thing. Here is the case the docs leave open: a member uploads at 9pm, printers are busy until morning, and a power blip hits at 2am. QUEUE-004 rebuilds state only from what printers are currently running, so the queued job is never recovered. Nothing in the specs tells the member it was lost, so they find out at pickup. That is the condition under which the tenet breaks, and the docs describe it. The mini-PC tenet (HLD:22) is the likely reason for the in-memory choice, but the two tenets conflict and the list is unordered (F7).

**F4 (medium). The choice has no Decisions row.** The in-memory queue is the kind of decision a cold reader would question, given the first tenet. It appears in the Architecture prose but not in Decisions & Alternatives (`job-queue-design.md:29–34`). The registry's table does record its SQLite choice and cost (`printer-registry-design.md:25`), so the job queue is the odd one out. A future session reading the table would not see that a tenet was traded against.

**Options for the tenet conflict.** The choice is yours. Any of these closes F2:
- **Change the design:** persist accepted jobs. The registry already uses a single SQLite file on the same mini-PC, so this may add a table rather than a new dependency. I haven't checked the implementation cost, though.
- **Record the exception:** add a Decisions row that names the tenet traded against and the condition, along the lines of "in-memory queue; accepted cost: undispatched jobs are lost on restart and members resubmit." Pair this with a spec that says what members are told, so the loss is not silent.
- **Revise the tenet:** narrow the promise to "once dispatched" or "once confirmed by the printer." Choose this only if losing queued jobs on restart is acceptable to you.

**What I'd recommend.** I'd lean toward persisting the queue. The first tenet and the overnight goal both depend on jobs surviving restarts, and the design already has the storage it would need. Recording the exception alone is honest, but it leaves the overnight goal unmet on a normal event. Whichever option you pick, add the Decisions row (F4). It is the smallest capture that settles the question, so this doesn't need a decision doc. If you keep the in-memory design, the row should also name the cost to members and what they are told.
