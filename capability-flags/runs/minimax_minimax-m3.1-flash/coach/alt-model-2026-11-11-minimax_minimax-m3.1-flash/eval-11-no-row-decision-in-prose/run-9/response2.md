**F2 — High. The accepted-job loss on restart is a live decision with no row, and it cuts against a tenet the HLD states outright.** `docs/intent/job-queue/job-queue-design.md:14` says the queue is "a per-printer-class list of accepted jobs held entirely in process memory," that startup recovery works by "polling each registered printer for the job it is currently running," and that "jobs that were accepted but not yet dispatched before a restart are gone, and members resubmit them." The operating condition is not hypothetical — `job-queue-design.md:10` states the mini-PC "takes unattended OS updates and the occasional power blip." So the sequence is: a member uploads in the evening per the HLD goal "Evening upload, overnight print, morning pickup," every printer in that class is busy, the job is accepted, the box reboots for an OS update overnight, and the job is silently gone. That directly undercuts the HLD tenet "A submitted job is a promise: members should be able to upload and walk away" — the promise is broken under a condition the docs themselves name. Under *docs carry current intent, written to be read cold*, this matters because the decision currently survives only as a clause in the Architecture paragraph: there is no row in Decisions & Alternatives, so a future session has no place to see it, no recorded cost, and no signal that the trade was made on purpose rather than overlooked. Under *tenets capture forward-looking preference*, the second problem is the sharper one — when a mechanism works against a stated tenet, the trade is supposed to be named. Right now a future agent reading this LLD sees "upload and walk away" in the HLD and "jobs are gone" in the LLD with nothing connecting them, so it will either silently re-derive a different design or treat the loss as a bug to fix. Either way the drift compounds: each session that reads the contradiction without a recorded reason is a session that could "helpfully" change the behavior in either direction.

Two adjacent findings ride on the same seam, and I'd resolve them in the same pass rather than leaving them to compound. **F6** — QUEUE-004 specifies rebuilding "farm state" by polling every printer for its current job, which is a second polling mechanism sitting beside the registry's 15 s heartbeat (`printer-registry-design.md:14`), and the second one bypasses the first; if jobs become durable, the startup poll's job narrows to recovering already-dispatched prints, and that should be stated rather than left for the next reader to infer. **F3** — the loss behavior has no spec at all, so "accepted jobs vanish on restart" is currently untestable and unenforced; QUEUE-004 covers only the rebuild half.

**On what I'd recommend.** Three remedies are legitimate here, and the choice is yours: change the design so accepted jobs survive (the registry already uses a single SQLite file, so the store exists — the cost is that the queue stops being "entirely in memory" and picks up a persistence failure mode), record the exception (a Decisions row naming the "a submitted job is a promise" tenet as the one traded against, plus a spec stating the loss behavior so it is intentional rather than silent), or revise the tenet so it means what the implementation does. My own recommendation is the second unless you're ready to pay for durability now — not because losing the jobs is fine, but because the tenet is written broadly ("upload and walk away") and the real constraint appears to be *when* the promise is kept: it holds once a printer has picked the job up, and breaks before that during a reboot. If that's the intended boundary, say so in the tenet, record the row, and add the spec — that turns an accidental contradiction into a designed, testable behavior. If the tenet was written to mean the job survives an overnight reboot, then the design needs to change and durability is the honest fix.

Whichever way you go, the minimum durable fix is the same two artifacts: a fuller Decisions row in `docs/intent/job-queue/job-queue-design.md` (chosen, rejected alternative, accepted cost, and the tenet it trades against) and a spec in `docs/intent/job-queue/job-queue-specs.md` for the restart behavior — currently something like *"When the service restarts, the system SHALL discard accepted jobs that were not dispatched"* if the exception is recorded, or a redesign of QUEUE-004 if they become durable. A decision doc is worth considering only if you want the option space on record — file-per-job, WAL-journalled queue, append-only log — because that's the level at which a future reader would want to re-run the choice; a table row is enough otherwise.
