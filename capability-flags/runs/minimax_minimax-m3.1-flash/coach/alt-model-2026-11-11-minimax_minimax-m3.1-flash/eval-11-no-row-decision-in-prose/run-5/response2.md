**F5 — High. The durability choice lives in prose, not in the design's memory, and it collides with your first tenet.** `docs/intent/job-queue/job-queue-design.md:14` states it in a single sentence: the queue is "held entirely in process memory … jobs that were accepted but not yet dispatched before a restart are gone, and members resubmit them." The same LLD's Context (`:10`) volunteers the condition that makes this bite — the mini-PC "takes unattended OS updates and the occasional power blip" — while the HLD's first tenet promises the opposite: "A submitted job is a promise: members should be able to upload and walk away" (`docs/high-level-design.md:20`), and the first goal is "Evening upload, overnight print, morning pickup — with no member present" (`:26`). Under *docs carry current intent, written to be read cold* — a doc states current intent as if authored fresh today by someone who knew only that intent — this is a real gap, because the LLD's Decisions & Alternatives table (`:29-33`) records the scheduling order, the job identifiers, and the upload size limit, and pointedly not the one decision that can lose a member's overnight job. The cold reader gets a behavior with no rationale and no accepted cost attached; the next session either re-litigates it or, worse, treats the loss as an oversight to be quietly "fixed" in code, which is exactly the drift *intent leads; code is compiled output* protects against — the spec would be edited to match the code rather than the code asked to honor the spec.

**The asymmetry with the registry is what makes this worth deciding rather than noting.** The printer registry persists its table in "a single SQLite file" (`docs/intent/printer-registry/printer-registry-design.md:14`), and uploaded G-code is kept "on disk under a content hash" (`job-queue-design.md:14`). So the design already persists two durable things on the same modest mini-PC and lets the third — the queue itself — evaporate. Worse, the blast radius isn't symmetric: after a blip the G-code *blob* is still on disk but the queue entry pointing at it is gone, so the service holds files it can no longer associate with any job, and nothing in the docs says they get reclaimed. The member's resubmission is cheap, yes — but "cheap" is a property of the blob store, not of the design as a whole, and the orphaned-blob outcome is a second, quieter consequence that no spec covers (it falls under F6). Under *effective intent-tree alignment* — specs trace to LLDs trace to HLD, and LLD behaviors with no spec are unnamed intent — a loss this consequential currently has no testable statement anywhere in the arrow.

**A cold reader will ask one question you haven't answered on the page: why can't the queue be rebuilt the way farm state is?** QUEUE-004 (`job-queue-specs.md:6`) rebuilds farm state by polling each registered printer for its current job, and the Architecture paragraph does the same — but the rebuild recovers what printers are *running*, not what the queue was *holding*, because the lost jobs were never sent anywhere. That's a perfectly reasonable answer, and it's precisely the reasoning that belongs in the Decisions table: it forecloses "why not just persist it like you persist the registry?" and it names the real boundary of what's recoverable. Right now that reasoning isn't on the page at all, so the design reads as though rebuild was intended to cover the queue and simply missed.

**Your three ways forward** — this is the tenet-conflict remedy set, and the choice is yours rather than mine, since each trades something different:

- **Change the design** — persist queue metadata (job, class, priority, position, content hash) in the same SQLite file the registry already owns, or a small append-only journal beside the G-code blobs. This makes the promise tenet true end-to-end and turns the existing disk layout into the durable substrate. The cost is real: it adds a write path and a schema to what was deliberately a "service stays small" design, and it raises the question of where that store lives — the registry currently owns it, so you'd be crossing the queue↔registry seam that F7 already flags, and the answer would probably be a shared store node or a deliberate single-owner rule.
- **Record the exception** — keep the in-memory queue and add a Decisions row that names the tenet being traded ("a submitted job is a promise"), says plainly that an accepted job can be lost to a restart, and justifies it against the tenet it trades with: the mini-PC is modest hardware (tenet 3), the overnight window means most queued jobs are re-submittable from a member's own copy, and the service prefers to fail small. This is the cheapest path, costs one table row, and makes the trade visible to every future session.
- **Revise the tenet** — narrow it so it no longer promises what the design can't keep, e.g. "a submitted job is a promise until the service restarts." I'd flag that this one costs you the HLD goal "morning pickup — with no member present," because a member who uploads before a blip must be present to resubmit, so the exception quietly moves into the goal.

**If you keep the in-memory queue, the minimum capture is one row plus one or two specs.** The row's shape is the same as your existing ones — Decision: "Queue durability across restarts" · Chosen: "In-memory queue; accepted-but-undispatched jobs are lost on restart" · Rationale: "Rejected: persisting queue metadata (the registry already writes SQLite on the same device, so the cost was mostly schema and write-path work); accepted cost: a member whose job is queued during a restart must resubmit, trading the 'a submitted job is a promise' tenet for the modest-hardware tenet. G-code blobs survive the restart under their content hash, so resubmission is cheap, but orphaned blobs are not reclaimed." Then the specs that make the behavior testable rather than implicit: one stating that on restart the system discards accepted-but-undispatched jobs, and one stating the blob-retention rule (who reclaims orphaned G-code, and when) — the second one is the piece that stops the disk quietly filling on a machine the tenets say to keep small. If you also want the member not to discover this by surprise, that requirement belongs in the queue view, which is currently owned by no design node at all (F4).

**If you change the design instead,** the arrow walk is straightforward but crosses a boundary: HLD tenet/goal stays as-is, the `job-queue` LLD's Architecture and Decisions change, new EARS land in `QUEUE-*` (durability and recovery), the persistence substrate needs an owner — which is the F7 question about whether the registry's SQLite file is the registry's alone or a shared farm store — and only then do tests and code follow. That last step is the one to settle first, since it decides where the write path lives.
