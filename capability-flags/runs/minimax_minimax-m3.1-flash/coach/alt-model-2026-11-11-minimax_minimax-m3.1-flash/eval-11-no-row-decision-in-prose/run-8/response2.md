**F3 — High. The queue's in-memory hold contradicts the HLD's own promise, and the LLD names the exact event that breaks it.** The HLD's first tenet is "A submitted job is a promise: members should be able to upload and walk away" (`docs/high-level-design.md:20`), and its first goal is "Evening upload, overnight print, morning pickup — with no member present" (`docs/high-level-design.md:26`); the Problem statement frames today's workflow as exactly the "hover until the print starts" chore the project exists to remove (`docs/high-level-design.md:5`). The job-queue LLD then designs against all three: the queue is "a per-printer-class list of accepted jobs held entirely in process memory," and "jobs that were accepted but not yet dispatched before a restart are gone, and members resubmit them" (`docs/intent/job-queue/job-queue-design.md:14`). The sharp part is that the same LLD supplies the trigger ten lines earlier — "the service runs on the workshop mini-PC, which takes unattended OS updates and the occasional power blip" (`job-queue-design.md:10`) — so the design has documented, in its own context section, that the promise's preconditions routinely fail overnight, and the failure mode is the member's job silently vanishing. This is a tenet conflict in the *tenet cascade* sense — the docs describe an operating condition under which a mechanism works against a tenet the HLD declares — and the inconsistency is asymmetric in a way that makes it worse: a job that has been *dispatched* survives the restart (it's running on the printer), while a job still *waiting* does not, so the failure window is precisely the overnight queue depth you designed for. The LLD did soften the blow with one good move — uploaded G-code is content-hashed on disk, so "resubmitting the same file is cheap" — but cheap resubmission still puts the member back online at 9pm, which is the thing the HLD says it wants gone.

**F5 — Medium. The choice itself has no row in the Decisions table, so the conflict is invisible to anyone who hasn't read this conversation.** `job-queue-design.md:29-33` records three decisions — scheduling order, job identifiers, upload size limit — and all three name their rejected alternative and accepted cost. None covers persistence. That omission matters because of how the *decision capture* principle works — the question is not "was this debated" but "would a cold reader of the landed design still question this choice, or want to reverse it?" A future agent reading "held entirely in process memory" next to a tenet promising uploads will absolutely question it, and the only places the reasoning could live are the LLD's prose (where it reads as a settled fact) and a chat session that isn't in the repo. Since the reasoning isn't recorded anywhere, the next session sees a contradiction and re-derives the design from scratch — or worse, "fixes" the spec to match the code and hardens the accidental behavior.

**On what to do.** Three remedies exist, and the choice is yours — but I'd steer you toward the first.

**1. Change the design: persist the queue.** Give the job-queue node its own durable store — a small SQLite file alongside the G-code content-hash store, matching the registry's existing "single SQLite file" convention (`printer-registry-design.md:14`) without sharing the file itself. Two files on a modest box costs nothing, and keeping the queue's store separate preserves node independence: the registry's row rationale ("nothing else needs concurrent writers") stays true, and the queue isn't writing into another node's table. The change lands inside the job-queue segment, so cascade is free there: `job-queue-design.md` gains the durability statement and a Decisions row naming the accepted costs (a disk write per accepted upload, and a queue that must be reconciled against printers on startup), and the spec file gains two lines — one for persisting at acceptance, one for reloading and resuming dispatch on startup — alongside the existing `QUEUE-004`, which already covers rebuilding farm state and would need to become a joint rebuild-and-resume rather than a poll alone. If you'd rather keep the queue's persistence and the registry's store in one file, that's a different shape: the shared-store decision has substance spanning two sibling nodes, so it belongs at the shared parent (the HLD) rather than inside job-queue, and it should be raised with you at that boundary rather than dropped in silently.

**2. Record the exception.** If in-memory is what you actually want — and it is a defensible choice for a six-printer makerspace with content-hashed G-code on disk — then keep the design and write the trade-off down where it belongs: a Decisions row naming the tenet traded against ("a submitted job is a promise"), why (simplicity on a modest box; cheap resubmission via content-hash), and the accepted cost (a queued job can be lost to an unattended reboot, and the member must resubmit). Pair it with a spec that makes the loss visible rather than silent — on startup the service records that the queue was reset, and the queue view tells members their pending jobs were lost — which buys back the "no silent" spirit of the second tenet even as it concedes the first. This remedy closes F5 at the same time, since the exception row is itself the decision capture.

**3. Revise the tenet.** Narrow it to something like "a submitted job is a promise *while the service is up*." I'd flag this as the weakest of the three: it weakens a tenet to accommodate a design choice rather than the other way round, and it leaves the "morning pickup with no member present" goal still defeated by the restart window.

**A note on sequencing.** Whichever you pick, the F1 finding interacts: all eight specs are currently marked `[x]` (implemented) while no code exists, so there's no implementation to argue with — the arrow's lower half is unwritten, which means changing the persistence design costs you one LLD edit and two or three spec lines, not a refactor. If you want to act on this, `/linked-intent-dev` is the right command for the design-and-spec change (Phase 2 for the LLD and its Decisions row, Phase 3 for the spec lines), and the edits will cascade into your eventual tests and code without those phases having to be unwritten first.
