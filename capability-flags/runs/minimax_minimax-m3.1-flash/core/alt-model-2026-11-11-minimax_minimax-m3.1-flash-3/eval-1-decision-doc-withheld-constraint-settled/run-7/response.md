**Phase 1 — HLD check** (`docs/high-level-design.md:13`): the architecture is unchanged — the registry already owned validation and lookup privately, and the HLD's "no runtime network access" tenet already ruled out the other two backends. One factual edit: the backend is now named (local embedded SQLite index) rather than "remains open".

**Phase 2 — Registry LLD revised** (`docs/intent/registry/registry-design.md`): the choice is recorded in the Decisions table with both rejected alternatives and their reasons; the LLD now specifies the index itself (`records` + `metadata` tables, self-contained file, no WAL sidecars so it renames as a unit), the all-or-nothing import (signature → schema version → SHA-256 records digest → candidate build → count/integrity → atomic rename), lookup normalization and the `NotFound`-vs-fault distinction, record validation rules, a nine-reason import failure taxonomy, and startup cleanup/recovery. The certificate interface is untouched, so no cascade into the certificates node.

I ran an edge-case probe over the draft (delegated to a subagent for unbiased coverage). It found real gaps; I closed the mechanical ones in the LLD — a missing records-digest verification step, the manifest being read from USB in place rather than copied, the first-import path and no-active-index lookup, the rename already unlinking the old index, the rename-vs-reopen contradiction, per-startup rather than per-lookup integrity checking, stale candidate files after a crash, out-of-space handling, and the record field and line-grammar rules. Two defaults I chose that you may want to overturn: normalization is **ASCII-only** whitespace and case (a pasted non-breaking space will not match), and a lookup already in flight during activation completes against the previous index and returns the previous snapshot date.

Four items need your judgment, and I left them open rather than deciding them:

1. **Result type for operational faults.** A kiosk with no snapshot yet, or with an unreadable index, currently has no value the declared `Found | NotFound` type can carry. Should `findBySerial` gain an explicit failure variant (which changes the certificate node's use of the result type), or should faults stay out-of-band beside the interface?
2. **Snapshot recency.** Should a validly signed snapshot older than the active one be allowed to replace it? Refusing protects against an accidental rollback onto stale calibration data; accepting allows deliberate re-imports and needs a rule for same-day dates.
3. **Import duration budget.** No target is set for rebuilding from a 150 MB snapshot on the kiosk.
4. **Operator feedback during a long import** — out of scope for this node since the kiosk interface isn't specified here.

Say how you want those four settled (and whether my two defaults stand), and whether to proceed to Phase 3, where I'll add the EARS specs for the new SQLite behaviors to `registry-specs.md`.
