No — I don't think it earns one, and I'd leave the choice recorded as a Decisions & Alternatives row.

The decision doc test is about the landed state: would a cold reader of the result question the choice or be tempted to reverse it? Here they wouldn't, because two of the three candidates were never viable in this environment to begin with. The HLD already says "All serial-number lookup SHALL complete using files on the kiosk; no runtime network access is permitted" and "Kiosks have no network route during normal operation", and its Non-Goals rule out "Live synchronization, remote access, or cloud services during kiosk operation." An on-site HTTPS directory and a managed search service both depend on a route the kiosks don't have. That is the "settled by an inherited constraint" case, which is explicitly the kind of choice that doesn't get a doc. It also affects only its own node — the certificate interface is unchanged, so no sibling segment has to reason about it or carry a cascade note. The Decisions & Alternatives row already names both rejected alternatives and why, which is exactly what a cold reader needs.

Worth naming the real reason it felt close: the option set was sketched without the tenet applied as a filter, so the two networked options looked like genuine contenders rather than already-excluded ones. That is worth keeping as knowledge, and it now lives in the row's rationale, which cites the no-network constraint, the kiosk having no route, and the recurring cost of the managed service — but it does not need its own artifact. The one thing that would change this answer is a change in the premise: if kiosks ever gain a network route, or the tenet is relaxed, the choice becomes live again and a decision doc would be warranted at that point.
