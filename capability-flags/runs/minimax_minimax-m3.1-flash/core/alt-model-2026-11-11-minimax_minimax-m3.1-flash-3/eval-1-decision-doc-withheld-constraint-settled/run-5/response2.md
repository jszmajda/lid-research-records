Overkill — and I'd argue the fact that you went back and forth is evidence *against* a doc, not for one.

The earns-its-place test asks what a cold reader of the landed result would do: question the choice, or be tempted to reverse it? A reader arriving at the registry design sees a tenet in the HLD that says all lookup completes from files on the kiosk with no runtime network access, and then a registry that uses a local embedded SQLite index. That reads as native — the constraint and the answer line up, and nobody re-litigates it. The doc would document a choice that explains itself.

There's also a specific disqualifier: the skill's rule says don't offer a doc for a choice an inherited constraint settles. The offline tenet eliminates both networked options outright, so the choice wasn't really a three-way tradeoff — it was "local file index, and SQLite is the obvious one." The real alternatives worth preserving were the ones *within* the local family: index shape, key derivation, failure shape. Those live in the Decisions table, and each is a genuine fork where a reader could reasonably ask "why this?"

The one place a doc could still earn its place is the **lookup failure shape** row. It changes the interface the certificates segment depends on, it has two plausible alternatives (third `Unavailable` case vs. separate failure channel), and a future maintainer might genuinely re-open whether a failure belongs in the result type at all. But it only clears the bar once that choice has settled and proven durable — right now it's a fresh fork, and I'd rather the table row carry it until there's history behind it.

What I did instead: tightened two table rows so the reasoning survives without the conversation. The backend row now names the tenet that settles it ("the tenet that all serial-number lookup completes from files on the kiosk... rules out both networked options") rather than just asserting kiosks have no network. The index-shape row had a claim that didn't survive scrutiny — I had written that an in-memory map would "repeat the build on every restart," which is wrong, since the raw snapshot isn't retained so it would need a durable store underneath anyway. It now says that.

One correction to something I implied earlier: I described the backend choice as settled by architecture, which was true, but I hadn't actually wired the *tenet* into the row's rationale. That's what made the choice look live to you in the first place — the row was arguing from "kiosks have no network" as a fact about kiosks rather than as a project constraint that governs the decision. That framing difference is probably what made the options look closer than they were.
