Written up as a decision record: `docs/intent/record-store/decisions/whole-visit-revisions.md` (owned by record-store, since the HLD leaves the concurrency mechanism there).

**What's in it**

- **Context** — why the store has to define a current state for independently corrected visits, and what's at stake on both sides: a blended value in a scientific export is invisible at the CSV, and too much review work pushes visits past Friday's export.
- **Decision elements** — three inherited gates (no submitted edit discarded; exported values traceable to a submission; no inference of scientific intent) and six weighted criteria (scientific integrity, traceability, coordinator workload, rule-maintenance cost, tablet cost, visits ready for export).
- **Three options in the domain**, each with its strongest honest case: **A** whole-visit revisions, **B** field-aware three-way merge, **C** serialize visits to one editor. B is eliminated by the third gate — deciding two edits are independent *is* the scientific inference the project doesn't want made automatically, and narrowing the rules until it's safe collapses B into A. C is eliminated by 48-hour disconnection.
- **Selection** — A wins on scientific integrity and traceability; its weakness is review workload, which is a quantity rather than a correctness problem. Forecloses automatic combination, merged-value provenance, and any export path emitting a value nobody submitted or selected.
- **Downstream obligations** — spelled out for both nodes:
  - *tablet-sync*: two identifiers per edited visit (base revision + last confirmed revision), a full snapshot per pending edit rather than a change set, **no automatic rebase** — a stale-base rejection goes back to the worker to re-apply, because a tablet that rebases would reintroduce the inference we removed — idempotent retries, and a worker-visible "accepted into review" state that doesn't present a pending revision as current.
  - *review-export*: a comparison screen that shows competing visits whole and does not construct a merged visit, a queue sized by conflict rate rather than visit count, held-out visits reported rather than silently absent, and a provenance trail naming the revision and any resolution on every exported row — with no mixed-origin columns, and a note on what an arbitrated-value extension would add.
- **Reconsidering** — B becomes defensible if relatedness is *declared* by the capture application rather than guessed from field names; that's the condition under which this decision should be re-run.

Also applied: the LLD's mechanism row and References now link the decision record; the HLD gained the tenet "Prefer an explicit human choice over a rule that combines observations automatically"; and site-catalog's stale "pending that choice" line is fixed, noting the store as a second consumer of the published snapshot for plot-reference validation.

Still open, and it's the one thing I'd want before writing the EARS specs: **resolution semantics** — the draft assumes a coordinator *selects* one submitted revision, so every exported visit is identical to a worker's submission. The alternative lets the coordinator submit an arbitrated payload (splitting a cover estimate, say), which is more flexible but means an exported value no worker asserted, needing a coordinator-authored marker in the CSV. Say "select" and I'll spec it; say "arbitrate" and I'll spec that instead. Then Phase 3: the REC specs for the revision model, acceptance rules, review groups, resolution, and export eligibility.
