# Decision: Change Delivery Mechanism

## Context

MarketBoard coordinates stall closures, power outages, and arrival statuses across 40 weekend markets. Up to 800 staff browsers simultaneously view board state, while 10–25 coordinators per market submit status updates. Normal activity averages two edits per minute, spiking to bursts of 20 edits per second during market opening.

The system requires committed edits to propagate to connected staff browsers reliably and quickly. Coordinators on the ground need fast visibility into stall statuses to manage active traffic and vendor placements. A disconnected browser must be able to catch up or detect that its view is stale. We must choose how committed changes are delivered from the authoritative server to client browsers.

## Decision Elements

- **Latency (major)**: How quickly a committed status change appears in connected browsers. The formal goal is under 15 seconds, but subsecond propagation is highly desirable for active event coordination during opening bursts.
- **Operational independence and vendor coupling (major)**: Avoiding third-party hosted service lock-in, external billing dependencies, proprietary client SDKs, or recurring usage-based fees.
- **Connection management complexity (major)**: The engineering and operational burden of maintaining concurrent client connections, heartbeats, socket resource limits, and reconnect storms across 800 simultaneous clients.
- **Client recovery and state catch-up (moderate)**: The complexity required for a client to detect connection loss, back off reconnects, and cleanly reconcile missed revisions after up to 20 minutes offline.
- **Server resource efficiency (minor)**: Server compute and network overhead generated by idle connections or redundant queries under normal traffic.

## Options in the Domain

### Five-Second HTTPS Polling

Browsers poll an HTTPS endpoint with a cursor (the last observed event revision) every five seconds. The server queries the change store for revisions newer than the cursor and returns empty or incremental results.

- **Latency**: Weak fit against major criterion. Inherent lag of 0 to 5 seconds (averaging 2.5 seconds) under normal operation, making subsecond updates impossible.
- **Operational independence and vendor coupling**: Strong fit against major criterion. Uses standard stateless HTTPS infrastructure with no third-party dependencies or external bills.
- **Connection management complexity**: Strong fit against major criterion. Fully stateless request/response cycle. No persistent socket states, connection pools, or idle connection limits.
- **Client recovery and state catch-up**: Strong fit against moderate criterion. Recovery is native to the polling mechanism; clients pass their latest revision cursor on each periodic fetch.
- **Server resource efficiency**: Weak fit against minor criterion. Continuous baseline request load (800 clients polling every 5 seconds yields ~160 requests/sec) regardless of whether changes occur.

*Summary*: Simplest stateless architecture, but imposes multi-second latency and continuous query overhead.

### Hosted Realtime Service

The application server publishes committed revisions to a managed third-party realtime pub/sub service (e.g., Pusher, Ably, Supabase Realtime). Client browsers maintain subscriptions via the provider's client library.

- **Latency**: Strong fit against major criterion. Provides subsecond, push-based delivery directly to connected clients.
- **Operational independence and vendor coupling**: Weak fit against major criterion. Introduces vendor lock-in, recurring operational costs that scale with connections and messages, provider credential management, and external availability dependencies.
- **Connection management complexity**: Strong fit against major criterion. Offloads persistent connection handling, WebSocket edge nodes, and socket scaling to the provider.
- **Client recovery and state catch-up**: Partial fit against moderate criterion. Requires reconciling provider presence/subscription events with internal authoritative revisions and handling reconnection fallbacks via standard server APIs.
- **Server resource efficiency**: Strong fit against minor criterion. Application server publishes each event revision once to the provider; minimal server compute spent on idle clients.

*Summary*: Fastest path to low-latency push updates with minimal socket operations, but sacrifices self-hosting independence and introduces recurring SaaS costs.

### Self-Hosted WebSockets

The application server manages persistent bidirectional WebSocket connections with connected browsers. Upon committing an edit to the change store, the server broadcasts the revision directly to active client sessions. Clients handle reconnects and request missed revisions over the socket using revision sequences.

- **Latency**: Strong fit against major criterion. Pushes committed revisions to active browsers immediately with subsecond latency.
- **Operational independence and vendor coupling**: Strong fit against major criterion. Fully self-hosted with no external realtime vendors, proprietary client SDKs, or usage-based billing.
- **Connection management complexity**: Partial fit against major criterion. The server must handle session tracking, heartbeat/ping-pong monitoring, socket limits, and graceful degradation under reconnect bursts. However, the scale (800 concurrent connections across 40 markets) is well within single-process capacity on modern runtimes.
- **Client recovery and state catch-up**: Partial fit against moderate criterion. Browsers must implement exponential reconnect backoff and issue replay requests with their last-received revision ID; the change store must maintain an ordered revision log to satisfy replays.
- **Server resource efficiency**: Strong fit against minor criterion. Idle connections consume minimal memory and bandwidth without polling queries hitting the database.

*Summary*: High-performance, low-latency push delivery that preserves total operational self-reliance, in exchange for owning socket connection management and replay logic.

## Selection

Self-hosted WebSockets is selected.

This choice trades the added engineering and operational responsibility of persistent connection management and client reconnect recovery for immediate, subsecond update delivery and full operational independence.

While HTTPS polling would simplify server operations, its multi-second lag degrades coordinator responsiveness during high-tempo opening periods, and baseline polling queries generate unnecessary constant load. A hosted realtime provider would relieve connection operations but conflicts with the preference for avoiding external vendor dependencies, recurring subscription costs, and third-party reliability coupling.

The operational scale of MarketBoard (800 concurrent browsers and peak write bursts of 20 edits per second) is modest enough that connection capacity and socket state can be handled reliably by standard application infrastructure without complex distributed broker clusters.

### Downstream Implications

- **Change Store (`docs/intent/change-store/`)**: Must maintain an append-only, ordered revision log for each event to support socket replay queries, along with publication triggers to dispatch committed edits to the delivery layer.
- **Delivery (`docs/intent/delivery/`)**: Must manage active WebSocket sessions, connection heartbeats, client authentication envelopes, and fan-out broadcasting for event revisions.
- **Browser Sync (`docs/intent/browser-sync/`)**: Must maintain the client WebSocket lifecycle, provide visual indicators of connection status (supporting the tenet: *connectivity failures must be visible*), implement exponential backoff on disconnect, and perform revision-gap replay or full snapshot reloads.
