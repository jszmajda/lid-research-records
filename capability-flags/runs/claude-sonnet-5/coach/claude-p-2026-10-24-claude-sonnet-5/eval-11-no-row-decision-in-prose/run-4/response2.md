**F1 — High. The in-memory job queue drops accepted-but-undispatched work on restart, and nothing records that this was a deliberate call.** `job-queue-design.md` states the queue is "held entirely in process memory," and that "jobs that were accepted but not yet dispatched before a restart are gone, and members resubmit them." That's a real design decision — it trades durability for simplicity — but the Decisions & Alternatives table only covers scheduling order, job identifiers, and upload size; there's no row for why the queue isn't persisted. Under *docs carry current intent* (a doc should read as current intent, written fresh — not leave live tradeoffs to be reconstructed from memory of a conversation), an unrecorded decision like this is exactly the kind of thing a future session re-derives or second-guesses from scratch, possibly landing on a different, contradictory answer than the one you actually chose. The fix here is usually small: add a row to the existing table — Decision: "Queue persistence," Chosen: "In-memory, rebuilt from printer polling on startup," Rationale: naming the rejected alternative (e.g., a persisted queue) and the accepted cost (jobs lost on restart, members resubmit). That's a row, not a decision doc — this doesn't need the full debate-on-record treatment unless you want one.

**F2 — High. That same design works against the HLD's own "a submitted job is a promise" tenet, under a condition the LLD names itself.** The HLD tenet reads: "A submitted job is a promise: members should be able to upload and walk away." But `job-queue-design.md`'s own Context section says the mini-PC "takes unattended OS updates and the occasional power blip" — and under exactly that condition, an accepted-but-undispatched job silently disappears and the member has to come back and resubmit it. That's not a hypothetical edge case; it's a condition the design doc already flags as expected to happen. Under *tenets capture forward-looking preference* — a tenet exists so a future session doesn't have to guess which way to lean when two choices are defensible — this is the situation a tenet is supposed to prevent drifting past unnoticed, and right now it's drifting past unrecorded.

For this one, the remedy is a genuine choice, not a prescription — pick whichever fits:
- **Change the design** — persist the queue (even something lightweight, like writing accepted-not-yet-dispatched jobs to the SQLite file the registry already uses) so a restart doesn't silently break the promise.
- **Record the exception** — keep in-memory, but add a Decisions row naming the tenet traded against and why (e.g., "mini-PC stays small" wins over strict durability, restarts are rare enough, resubmission is cheap given content-hashed uploads). This closes F1 and F2 in the same row — once the tradeoff is written down, the tenet conflict is also resolved for a cold reader, since they can now see it was a deliberate accepted cost rather than an oversight.
- **Revise the tenet** — if "upload and walk away" was always meant to mean "accepted jobs survive dispatch, not necessarily a crash," narrow the tenet's wording so it stops promising more than the system does.

I'd lean toward the second option given the project's own "stays small" tenet and the mini-PC constraint — but that's your call, not mine to make for you. Either way, this isn't a config change, so there's no `/update-lid` here — it's a docs edit you'd make directly in `job-queue-design.md` (and possibly `high-level-design.md` if you revise the tenet).
