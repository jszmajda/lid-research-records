Here's the detailed walk-through for F1 and F2 — both trace back to the same mechanism, so I'll take them together.

**F1 — High. The in-memory job queue drops accepted-but-undispatched work exactly when the system says it will restart.** `job-queue-design.md`'s Architecture section holds the queue "entirely in process memory" and states plainly that "jobs that were accepted but not yet dispatched before a restart are gone, and members resubmit them." That's not a hypothetical edge case — the same doc's Context section tells you the mini-PC "takes unattended OS updates and the occasional power blip." So the condition that triggers data loss is a described, expected fact about this machine, not a rare failure mode. Under *tenets capture forward-looking preference* — a tenet is a one-line tie-breaker for exactly this kind of call — the HLD's own first tenet reads "A submitted job is a promise: members should be able to upload and walk away." A member who uploads a job in the evening, goes to bed, and wakes up to find it silently vanished because the mini-PC took an OS update at 2am is the precise failure the tenet was written to rule out. This matters because the tenet exists to pre-narrow exactly this kind of design call — in-memory-vs-persisted queue state — and here the mechanism leans the opposite way from the tenet without anyone having decided that on purpose. Left alone, the gap will surface as a support complaint from a real member before anyone connects it back to a design doc.

**F2 — High, same mechanism. The trade-off isn't recorded anywhere a reader would look for it.** `job-queue-design.md`'s Decisions & Alternatives table has three rows (scheduling order, job identifiers, upload size limit), and none of them cover "why is the queue in-memory rather than persisted, given restarts happen." Under *docs carry current intent* — the test being, would a cold reader of the landed design still question or want to reverse this choice — anyone reading this LLD next to the HLD's tenets would stop on this one. Right now that question only has an answer if you go find whoever wrote the doc and ask them; the doc itself doesn't say whether persistence was considered and rejected (e.g., for simplicity on modest hardware) or whether this is just an oversight. That ambiguity is exactly what decision capture exists to close, and per the remedies here, it closes both findings at once if you record it.

**What I'd recommend:** this is a case where the fix is the user's call among three options, not mine to pick —
1. **Change the design** — persist accepted-but-undispatched jobs (even something lightweight, like writing accepted jobs to the same on-disk content-hash store already used for the G-code files) so a restart doesn't lose them.
2. **Record the exception** — if in-memory-only is the deliberate choice (e.g., to keep the mini-PC's footprint small, echoing the "service stays small" tenet), add a Decisions & Alternatives row naming the tenet traded against and why — e.g., "Accepted-but-undispatched jobs are lost on restart | In-memory only | Persisting queue state adds disk-write overhead and a recovery path on a machine that already takes unattended updates; accepted cost: members resubmit after a restart, which conflicts with the 'walk away' tenet but keeps the service simple."
3. **Revise the tenet** — if "upload and walk away" was never meant to survive a restart, soften it so it doesn't overclaim.

Recording the exception (option 2) would resolve F2 as well, since it gives the decision a home.
