**Reconstructed EARS requirements — mark read-back keying / duplicate-symbol handling (sheets-view: `render_positions`, `ViewError::DuplicateSymbolRow`, `read_marks`)**

**Ubiquitous:** The Positions view tab SHALL contain exactly one row per distinct ledger `Symbol` present in `Snapshot.positions`; each row's Symbol cell is the row-identity key that the marks read-back settle pass (`read_marks`) correlates against. The uniqueness check operates on the raw ledger `Symbol`, not the alias-resolved `GOOGLEFINANCE` ticker — two distinct symbols that resolve to the same ticker string are NOT considered duplicates and each still receives its own row.

**Unwanted behavior:** IF `render_positions` is about to emit a row for a `Symbol` already emitted earlier in the same call (i.e., the one-row-per-symbol invariant is violated), THEN the system SHALL immediately abort and return `Err(ViewError::DuplicateSymbolRow(symbol))` carrying the offending symbol's exact `String` value, and SHALL NOT emit a duplicate row, merge/average/sum the conflicting entries, silently drop either entry, or return a partial `ViewTab`.

**State-driven:** WHILE `Snapshot.positions` is sourced as a `Map<Symbol, _>` (uniqueness guaranteed by construction), the duplicate-row check SHALL be a defensive, structurally-unreachable safeguard on the real code path (confirmed by tests: happy path with multiple distinct symbols always yields distinct rows) — it exists only against a hypothetical future non-`Map` position source, not as a live-data invariant expected to trip.

**Ubiquitous (error format):** `ViewError::DuplicateSymbolRow`'s `Display` output SHALL equal its derived `Debug` output verbatim: format `DuplicateSymbolRow("<symbol>")` (test-pinned exactly to `DuplicateSymbolRow("AMZN")` for symbol `"AMZN"`), via the `{self:?}` passthrough in the `Display` impl.

**Event-driven:** WHEN `read_marks` is invoked with a `symbols: &[Symbol]` slice, THE system SHALL treat that slice as the exhaustive, one-entry-expected-per-symbol set of row keys to settle, correlating each `PricePass` reading and each cached `prior: &BTreeMap<Symbol, Mark>` entry by exact `Symbol` equality (`BTreeMap` key lookup). `read_marks` performs NO independent duplicate-detection or dedup over `symbols` itself — the uniqueness of the row-key space is assumed to already hold, guaranteed upstream by `render_positions`'s guard (or its caller passing `Snapshot.positions`' keys) before marks are ever requested. There is no case-folding, trimming, or other normalization of the `Symbol` string anywhere in this keying path — comparison is exact string/byte equality via `Ord`/`Eq` on `Symbol`.
