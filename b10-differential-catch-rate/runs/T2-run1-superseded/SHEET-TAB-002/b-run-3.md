**EARS reconstruction — workbook tab ordering on republish**

**Ubiquitous — canonical order.** The system SHALL define one canonical workbook tab order via `workbook_tab_order()`, consisting of exactly these 10 tabs in this fixed sequence: `Positions, Open Lots, Realized, Tax, History, Tax Rules, Residency, Platforms & Aliases, Ledger Events, Tax Events`. Within it: Positions SHALL be the leftmost/landing tab; the four view tabs SHALL precede everything else, in that order; `History` SHALL immediately follow the views; the three config tabs SHALL follow History in the fixed sub-order `Tax Rules < Residency < Platforms & Aliases`; the two event-log tabs SHALL be last, with `Ledger Events` before `Tax Events`, and `Tax Events` SHALL be the final tab overall. (The Tax tab's reserve-summary band, `TAX_RESERVE_TAB`, is not a member of this order.)

**Event-driven — reassert on every republish.** WHEN `Publisher::republish` runs and successfully acquires the advisory write-lock, the system SHALL call `set_tab_order` with the FULL canonical order (not the subset of tabs passed into `republish`) exactly once, after attempting `batch_update_view` for every tab in the call — regardless of whether any individual tab write succeeded or failed. Order reassertion is unconditional and idempotent: two consecutive republish cycles SHALL leave the workbook's tab order identical to the canonical order.

**State-driven — lock held elsewhere.** WHILE the write-lock cannot be acquired (held by another writer, or an acquisition I/O error), the system SHALL perform no tab writes and no order reassertion for that cycle, returning `published: false` with the stale set unchanged.

**Unwanted behavior — order-write failure.** IF `set_tab_order` returns an error, THEN the system SHALL mark the cycle's `RepublishOutcome.published` as `false`, but SHALL NOT add any tab to `stale_tabs` or write a stale banner on account of the order failure alone — that mechanism is reserved for per-tab `batch_update_view` failures.

**Unwanted behavior — production no-op.** The production `ViewSheetsAdapter::set_tab_order` SHALL always return `Ok(())` and perform no workbook-metadata mutation (documented: the low-level Sheets primitive models only the values grid, not sheet-order metadata) — i.e., order reassertion currently has no effect through the real adapter. Only the in-memory test double (`InMemorySheetsView`) actually records `set_tab_order`'s argument as the tab order and can be made to fail it (`set_order_fails`), which tests use to assert the failure semantics above.
